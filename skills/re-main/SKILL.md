# Rebase on main

One invocation, full flow: git rebase + project-specific cleanup.

## Detect the project

**Default branch.** Find it before anything else:

```sh
git symbolic-ref --short refs/remotes/origin/HEAD
```

(If that's unset, use `git remote show origin` and read the "HEAD branch" line.) Every command below is written for `main` — substitute `master` (or whatever came back) throughout if the repo differs.

**Capabilities.** Each later section applies only if its files exist in the repo:

- `demo/days/*.sql` / `demo/days/*.sorted` snapshots → the demo conflict auto-resolution and the demo regeneration note.
- `backend/src/*/openapi.yaml` with a generated `frontend/src/Api/Data.elm` → the codegen conflict auto-resolution and the regen step.
- `backend/src/*/db/versions/` → the alembic sections.
- `codegen` / `dist` / `check` targets in the backend and frontend Makefiles → the regen and verify commands.

If none apply, do pre-flight and the rebase only: auto-resolve **nothing** — every conflict goes to the user — then run whatever check/build targets the project's Makefile or README documents, and report.

Auto-resolution principle: take the rebase target's side only for files that are fully regenerated by a build step. Never extend the generated-file list by guessing — if an unlisted file looks generated, ask.

## Pre-flight

### Find the rebase target

**Do this before touching anything.** A branch is not necessarily based on the default branch: in a stacked PR, its base is the branch below it. Rebasing a stacked branch onto the default branch swallows the parent's commits into it, orphans the parent PR, and leaves the children pointing at commits that no longer exist.

The branch's own PR base is the source of truth:

```sh
BRANCH=$(git branch --show-current)
gh pr view "$BRANCH" --json baseRefName,number,title
```

- **`baseRefName` is the default branch** → ordinary branch. The **rebase target** is `origin/main`.
- **`baseRefName` is anything else** → this is a **stacked PR**. The **rebase target** is `origin/<baseRefName>`, never `origin/main`. Say so out loud before proceeding: "PR #N is based on `<baseRefName>`, so rebasing onto `origin/<baseRefName>`."
- **No PR exists for the branch yet** (`gh` reports "no pull requests found") → fall back to the default branch as the rebase target, and **tell the user** you did, so they can correct you if the branch is really stacked on an unpushed parent.
- **The `gh` call fails for any other reason** (not authenticated, network, API error) → **stop**. Do not assume the default branch; report the error and let the user fix it.

Everywhere below, "the rebase target" means the ref resolved here. Fetch it, and substitute it for `origin/main` in every command — including every merge-base and every commit range.

```sh
TARGET=origin/<baseRefName or default branch>
git fetch origin "<baseRefName or default branch>"
```

### Never range against the default branch on a stacked branch

Every commit range in this skill — `git merge-base`, `$TARGET..HEAD`, `$TARGET...HEAD` — is computed against **the rebase target**, never against `origin/main` when they differ. A range taken from `origin/main` on a stacked branch spans the stack boundary and includes the parent branch's commits.

The squash case is the one that has actually destroyed work: implementing "squash the branch's commits into one" as

```sh
git reset --soft $(git merge-base origin/main HEAD)   # WRONG on a stacked branch
```

collapses the **parent PR's** commits into this branch's single commit. The parent is left orphaned, this branch's rendered diff against its base becomes meaningless, and the children point at a commit that no longer exists. The correct form is always

```sh
git reset --soft $(git merge-base "$TARGET" HEAD)
```

Same for listing branch-added migrations, diffing what the branch changed, counting commits — all of it against `$TARGET`.

### Record a recovery point

Before any history rewriting, capture the current tip so there is a named recovery point besides `ORIG_HEAD` (which later git operations overwrite):

```sh
PRE_REBASE=$(git rev-parse HEAD)
echo "pre-rebase tip: $PRE_REBASE"
```

Print it, and repeat it in the final summary. `git reset --hard $PRE_REBASE` restores the branch exactly.

### Checks

Refuse to start unless all of these hold. If any fails, explain the problem and stop.

1. `git status` shows a clean working tree (no staged or unstaged changes, no conflicting untracked files). If dirty, tell the user to commit or stash first — never auto-stash.
2. Current branch is **not** the default branch. If it is, stop.
3. The branch has commits ahead of the rebase target. If `git rev-list --count "$TARGET"..HEAD` is 0, the branch has nothing to rebase; say so and stop.
4. The rebase target has moved. If `git rev-list --count HEAD.."$TARGET"` is 0, the branch is already on top of it — say so and stop.

### Find the descendants

Other open PRs may be based on this branch. They will be orphaned by the rebase, so find them now, while their old base commit is still the branch tip:

```sh
gh pr list --state open --json number,headRefName,baseRefName
```

Every PR whose `baseRefName` equals the current branch is a **child**. Record each child's `headRefName` together with `$PRE_REBASE` — that pair is what restacks it later. Children of children are stacked the same way; walk the list transitively so you know the whole stack before starting.

If the branch has children, say so in the plan: they will each need a restack after this rebase.

## Plan the work

Look at what the rebase target added since the branch diverged so you know what regeneration to expect later:

```sh
BASE=$(git merge-base HEAD "$TARGET")
git diff --name-only "$BASE" "$TARGET"
```

Note whether the target's diff contains any of:

- `backend/src/*/db/versions/*.py` — new alembic migration
- `demo/days/*.sql` or `demo/days/*.sorted` — demo snapshot changes
- `backend/src/*/openapi.yaml` — API spec changes

### Read the story behind the branch

Conflicts are decided by intent, not by which side looks newer, so load the intent before the rebase rather than mid-conflict. Collect the issues the branch's commits reference:

```sh
git log --format=%B "$TARGET"..HEAD | grep -o 'Refs [^ ]*#[0-9]*'
```

For each, read the story and its acceptance criteria:

```sh
gh issue view <issue> --json title,body
```

Keep those ACs at hand: they are the tiebreak for any conflict in a hand-written file, and the checklist for the post-rebase verification.

State the plan in one short paragraph before running the rebase so the user can sanity-check it: the rebase target and why, the pre-rebase tip, what the target brings in, the children that will need restacking, and the story the branch implements.

## Run the rebase

```sh
git rebase "$TARGET"
```

Loop until rebase completes or you hit a conflict that needs the user. After each `git rebase --continue`, re-check for the next conflict.

The two auto-resolutions below apply only to the generated files detected in "Detect the project".

**Conflict only in `demo/days/*.sql` / `demo/days/*.sorted`** — take the rebase target's version. These are auto-generated; hand-merging them produces nonsense.

```sh
git checkout --ours -- demo/days/
git add demo/days/
git rebase --continue
```

(During a rebase, `--ours` is the upstream side = the rebase target's version, `--theirs` is the commit being replayed.)

**Conflict in `frontend/src/Api/Data.elm`** — take the rebase target's version; it'll be regenerated below.

```sh
git checkout --ours -- frontend/src/Api/Data.elm
git add frontend/src/Api/Data.elm
git rebase --continue
```

**Both sides renamed the same migration file to different names** — this happens when a later commit on the branch already carried its own rename of a migration that the "Update branch migration dates" step below also renames. Keep the newer date this skill is applying and drop the older rename, so the file exists exactly once. Then re-run the static graph check in "Alembic migration rebase" before continuing — a dropped rename can leave a `down_revision` pointing at the wrong file.

**Conflict in any hand-written file** (source code, `openapi.yaml`, migration files, anything else) — do **not** guess, and do not resolve by whichever side looks newer. Two conflicting sides can encode two different intents, which makes the resolution a product question, not a mechanical one. Before proposing anything:

1. Run `git status` to surface the conflicts.
2. Re-read the story from "Read the story behind the branch" — the `Refs #N` issue(s) for the commit being replayed (`git log -1 --format=%B REBASE_HEAD`), via `gh issue view`.
3. Resolve, or propose a resolution, **in terms of what that story specifies**. The issue's acceptance criteria are the tiebreak.
4. If the story doesn't settle it, ask the user, and say which AC you were unable to match the sides against.

### After every resolution, check for leftover markers

After **any** conflict resolution — including the auto-resolutions above — verify no conflict markers survived anywhere in the tree before continuing:

```sh
git grep -n '<<<<<<<\|>>>>>>>\|^=======$'
```

Any hit is an unfinished resolution: fix it before `git rebase --continue`. (Filter out the rare legitimate hit — e.g. a fixture that documents conflict markers — but do not skip the check.)

If the rebase is unrecoverable, run `git rebase --abort`, and if that leaves anything off, `git reset --hard $PRE_REBASE`. Report what went wrong.

## Update branch migration dates

If the branch added any alembic migrations, their filename date prefix and `Create Date:` docstring still reflect when the branch was first cut — which can be weeks ago. Rename them and update the comment so they sort after the rebase target's latest migration.

List branch-added migrations:

```sh
git diff --name-only --diff-filter=A "$TARGET"...HEAD -- 'backend/src/*/db/versions/'
```

If empty, skip this section. Otherwise, find the newest migration filename on the rebase target:

```sh
git ls-tree --name-only "$TARGET" -- 'backend/src/*/db/versions/' | sort | tail -1
```

Then, for each branch-added file `YYYY_MM_DD_<revision>_<name>.py`:

1. Get today's date in both formats: `date +%Y_%m_%d` (filename) and `date +%Y-%m-%d` (comment).
2. Pick the new date prefix. Filenames sort lexicographically, and a same-day tie is broken by the rest of the filename — `2026_09_21_5649…` sorts *before* an existing `2026_09_21_86b0…` — so today is not automatically sufficient. The new prefix must make the filename **strictly greater** than the target's newest migration filename; if today's date ties and the revision part loses the comparison, use the next day instead.
3. Rename the file: replace the leading `YYYY_MM_DD_` with the chosen date (keep the revision and name parts unchanged).
4. Edit the `Create Date: YYYY-MM-DD HH:MM:SS.NNNNNN` line in the docstring: replace only the date portion with the chosen date; keep the time portion as-is (it's arbitrary, and changing it would falsely imply alembic was re-run).

Use `git mv` for the rename so the file history is preserved.

Skip any file whose date prefix already sorts strictly after the target's newest migration.

## Alembic migration rebase

Skip this entire section if the branch added no migrations:

```sh
git diff --name-only --diff-filter=A "$TARGET"...HEAD -- 'backend/src/*/db/versions/'
```

If empty, jump to "Regenerate codegen".

### Static graph check

Pre-check the migration graph statically — no DB, no nix-shell needed — to catch a stale `down_revision` left by the rebase:

```sh
python backend/src/*/scripts/check_migrations.py
```

(Skip the static check if the script doesn't exist — not every project has it. Still run the DB verification below.)

- **`OK: N migrations form a single valid chain.`** — graph is fine, move on to DB verification.
- **`Multiple Alembic heads`** or **`references revision '<rev>', which does not exist`** — the rebase left a stale `down_revision`. Fix it:

1. Find the rebase target's new head:
   ```sh
   cd backend && nix-shell --run "alembic -c etc/development.ini heads"
   ```
2. Edit the earliest branch-added migration's `down_revision = "..."` to point to that head. Don't touch the chain of branch migrations after that — they stay chained to each other.
3. Re-run the static graph check and confirm it prints `OK: ...`. If not, fix and re-run before touching the DB.

### DB verification

Run the branch's migration against a DB freshly seeded to the rebase target's schema. This catches real schema conflicts the static check can't see (e.g. same column added on both sides) and validates the migration against the schema state production will be in.

1. Make sure Postgres is running. If `pg_isready` fails (or the equivalent), start it:
   ```sh
   cd backend && nix-shell --run "make up"
   ```
2. Seed the local DB to the rebase target's schema. On an ordinary branch that's local `main`; on a stacked branch, check out the parent branch instead — the branch's migration chains onto the parent's, not onto main's.
   ```sh
   BRANCH=$(git branch --show-current)
   git fetch origin <target branch>:<target branch>
   git checkout <target branch>
   cd backend && nix-shell --run "make devdb"
   git checkout "$BRANCH"
   ```
   (`git fetch origin X:X` updates the local branch without checking it out — works even when it has diverged, since we're not on it. If that fails for any reason, fall back to `git checkout X && git reset --hard origin/X`.)
3. Apply the branch migrations on top:
   ```sh
   cd backend && nix-shell --run "alembic -c etc/development.ini upgrade head"
   ```

If `alembic upgrade head` fails, stop and report — the migration has a real conflict with the target's schema, which needs user judgment.

If `make devdb` fails, the DB verification is meaningless; flag it in the final summary so the user knows the branch migration is unverified.

## Regenerate codegen + rebuild frontend

If the project has the `codegen` and `dist` targets, always run these two, in this order — regardless of what the rebase target changed. Running `make codegen` first guarantees `frontend/src/Api/Data.elm` matches the rebased `openapi.yaml`, which then lets `make dist` compile cleanly in a single pass (no "run it twice" workaround). **Always through `nix-shell`**, not `devenv` or `make` directly — devenv has a stale-cache issue that produces "unknown alias" / missing-constructor errors after openapi-generator runs.

```sh
cd backend && nix-shell --run "make codegen"
```

```sh
cd frontend && nix-shell --run "make dist"
```

This also ensures `backend/src/*/static/dist` reflects the rebased source — any change the target brought in to a `.elm` file or `tailwind.config.js` gets picked up.

## Demo SQL regeneration

If `demo/days/*.sql` was touched on either side (or you took the target's during conflict resolution), the snapshots no longer reflect the branch's state.

Don't run `make demo` yourself — it needs an interactive browser session and is slow. Surface it as the explicit next step in the final summary instead.

## Verify

```sh
cd backend && nix-shell --run "make check"
cd frontend && nix-shell --run "make check"
```

If either reports a diff on a generated file, that means a regen step above was skipped. Re-run the right step rather than `git checkout`-ing the diff away — the diff *is* the signal.

Then two more verifications the mechanical checks can't cover:

1. **No conflict markers anywhere**, one final time: `git grep -n '<<<<<<<\|>>>>>>>\|^=======$'`.
2. **The story still holds.** Re-read the ACs collected in "Read the story behind the branch". Where an AC names specific behaviour, confirm the rebased branch still satisfies it — a conflict resolved toward the target's side can quietly drop the very behaviour the story asked for. Report any AC you could not verify.

## Restack the descendants

If the pre-flight found child PRs based on this branch, they are now pointing at `$PRE_REBASE`, which is no longer in this branch's history. They must be restacked, or GitHub renders each child's diff against a base commit that no longer exists.

For each direct child, in stack order (parent first, then its children, then theirs):

```sh
git rebase --onto <new tip of the rebased parent> "$PRE_REBASE" <child branch>
```

where `<new tip of the rebased parent>` is `git rev-parse <parent branch>` after its rebase, and `$PRE_REBASE` is the parent's tip recorded *before* it. Record each child's own pre-rebase tip the same way before restacking it, since its children need it in turn.

Every conflict rule above applies unchanged to a restack, including the conflict-marker check.

If you'd rather not touch other branches without asking — or a restack conflicts in a hand-written file — stop and tell the user **exactly which branches now need a restack, in which order, and with which `--onto` arguments**. An unrestacked child is the failure mode this section exists to prevent; never end the run silently leaving one behind.

**Rebase and push bottom-up.** Rebase the lowest branch in the stack first, then each child in order, and push in that same order, so GitHub never shows a child whose base commit isn't there yet.

## Output

End with:

1. Branch name, the rebase target and why it was chosen (default branch, or the parent of a stacked PR), and what was rebased: `N commits replayed on top of <target> at <SHA>`.
2. The recorded pre-rebase tip `$PRE_REBASE`, spelled out as the recovery command: `git reset --hard <SHA>`.
3. What from the target triggered branch-specific work (alembic chain fixups, demo SQL conflicts). Note that `make codegen` and `make dist` are always run when present, so no need to call them out unless they failed.
4. Conflicts encountered and how they were resolved (auto-taken from the target, resolved per the story's ACs, or user-resolved), and confirmation that the conflict-marker check is clean.
5. Whether `make check` is clean in the affected subdirectories, and whether the story's ACs still hold.
6. Child branches: restacked (with their new bases), or the exact commands the user still needs to run, in order.

Do **not** push, force-push, or amend. Leave the post-rebase working-tree changes (renamed migrations, regenerated codegen) uncommitted on purpose: the intended flow is that the user amends them — together with fresh demo snapshots, if any — into the branch commits before pushing.

When the user does push, it must be `git push --force-with-lease`, never a bare `--force`: `--force-with-lease` refuses the push if the remote moved since the last fetch, which is the only thing standing between a rebase and someone else's commits. Say this in the summary. Push bottom-up through the stack.

If demo snapshots are stale, close by asking explicitly: will the user run `make demo` now (then amend everything together), or amend and push without it?
